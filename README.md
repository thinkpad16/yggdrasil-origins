# Yggdrasil Origins

A standalone class system for the **Minestar Yggdrasil (FallenEden)** RPG pack.
Minecraft **1.21.1**, Fabric.

Origins is **not required**: the choice, its storage, the picker screen, the commands and the
power engine are all ours. Abilities are plain JSON data; the mod reads them, grants them and
runs them itself.

## What the pack needs

| Mod | What for |
|---|---|
| `fabric-api` | events, networking, resources, data attachments — **the only hard dependency** |
| RPG stack (`spell_power`, `spell_engine`, `mrpg_lib`, `attributes_ld`, `combat_roll`, `ranged_weapon_api`, `critical_strike`) | **soft** (`suggests`): attributes of other systems — magic school power, proc chances, rolls, bows. If a mod is absent its modifiers are skipped and the rest of the class still works |

Origins and Apoli are not needed at all. If Origins is still installed the mod leaves it alone
and a built-in datapack silences its default origins.

There is no external attribute the mod breaks without. Swim speed
(`yggdrasil_origins:swim_speed`) is **deliberately not a real attribute**: the player attribute
supplier is built once at startup, and if another mod touches it before our registration runs,
the attribute simply would not exist on the player (which is exactly what happened in a pack
with the RPG stack — the value vanished because of load order). The engine computes the
multiplier itself and `SwimSpeedMixin` applies it: from the engine on the server, from a synced
number on the client so movement does not stutter. The data format is unchanged — powers still
use the same id.

## Core principle

**Almost nothing needs Java.** Classes, selection layers and abilities are JSON; the Java side
is a thin shell: a data registry, choice storage, packets, the screen, the commands and the
engine that executes the data.

## Layout

```
src/main/resources/
  fabric.mod.json
  assets/yggdrasil_origins/
    icon.png                      mod icon
    lang/*.json                   every player-facing string (en_us, uk_ua)
    textures/entity/visual_parts.png   generated by tools/gen_visual_texture.py
    textures/gui/impact/*.png     impact tier icons
  data/yggdrasil_origins/
    classes/*.json                classes: {"icon": {...}, "impact": 0..3, "order": N,
                                            "powers": [...], "visual": {...}}
    selection/*.json              layers: {"order": N, "required": true, "default": "...",
                                           "entries": [{"id": "...", "requires": "<class>"}]}
    powers/*.json                 abilities (Apoli-shaped JSON)
    recipe/class_orb.json         the respec orb recipe
    tags/{item,block}/*.json      our own tags

src/main/java/.../
  clazz/ClassRegistry.java        reads classes/ and selection/ from any datapack
  clazz/ClassManager.java         stores the choice, grants powers, pushes the picker
  power/PowerEngine.java          the ability engine
  power/{Actions,Conditions,DamageConditions,PowerState,HudSync}.java
  visual/*.java                   the single source of class looks (render + hitbox)
  mixin/*.java                    only into vanilla, never into other mods
src/client/java/.../
  client/ClientClasses.java       client snapshot of the registry
  client/ClientHud.java           ability bars
  client/gui/ClassSelectScreen.java  picker and the read-only "my class" screen
  client/render/VisualParts*.java geometry and rendering of the visual parts
```

Any datapack can add its own classes: drop
`data/<your_namespace>/classes/<id>.json` and add an entry to `selection/class.json`.

## Checklist before a server launch

1. **`/ygg doctor`** must answer "No problems found". Classes rely on attributes from seven
   third-party mods (`attributes_ld`, `spell_power`, `spell_engine`, `mrpg_lib`, `combat_roll`,
   `ranged_weapon_api`, `critical_strike`). If one is removed, or renames an attribute in an
   update, part of the abilities **silently stops working** while the tooltip still promises the
   bonus. The command names both the attribute and the affected classes. The same goes into the
   log as a single line at startup — but only when there is a problem.
2. **If Origins is installed**, keep the datapack `yggdrasil_origins:disable_vanilla_origins`
   enabled (it is by default), otherwise players are asked about their origin twice.
3. **The "My Class" key is L.** Not O: in Origins the O key is already "view origin" and one
   press would open two screens. It is rebindable, and `/yggclass` does the same.
4. **The class orb is craftable**: 4 gold ingots + an eye of ender. That is a free respec for
   anyone with gold. If you do not want that, override
   `data/yggdrasil_origins/recipe/class_orb.json` with a datapack, or remove it with CraftTweaker.
5. **Ability bars** are toggled by the player with `/ygghud`, class looks with `/yggvisuals`.
   Neither concerns the server; nothing needs reloading.
6. **`/ygg stats`** shows how players are spread across classes — the most useful number for
   balancing a live server; **`/ygg perf`** shows what the engine costs per tick.

Note: Apoli, if installed, will read our power files, because they sit in the usual
`data/<namespace>/powers/` folder. They are all written with `apoli:*` types, so they parse
cleanly and simply stay unused — no effect on the game or the log.

## Commands

```
/ygg gui [player]                    open the picker
/ygg set <player> <layer> <class>    set a class (OP)
/ygg clear <player>                  clear the choice (OP)
/ygg get <player>                    what the player has chosen (OP)
/ygg has <player> <class>            does the player have that class (OP)
/ygg random <player> [layer]         pick a random available class (OP)
/ygg powers <player>                 list the granted abilities (OP)
/ygg give <player>                   hand out a class orb (OP)
/ygg cooldowns <player> clear        reset all ability cooldowns and resources (OP)
/ygg stats                           class spread among online players (OP)
/ygg doctor                          health report: missing attributes, broken data (OP)
/ygg perf [reset]                    engine cost per tick (OP)
/ygg debug <player>                  ask the engine directly about one player (OP)
/ygg list                            how many classes and layers were read
/yggclass                            the read-only "my class" screen (client)
/yggvisuals [on|off]                 class looks on this client
/ygghud [on|off]                     ability bars on this client
```

Wherever `<player>` appears, **any target** is accepted: a name (`Tester` — the case where
another mod substitutes `{player}`), `@s`, `@p`, `@a`, `@r` and filtered selectors
(`@a[team=red,limit=5]`). The command runs for **every** matched player and the return code is a
count: players for `set`/`clear`/`give`, matches for `has`, abilities for `powers`. That makes
them useful inside `execute store result score …` and `execute if`.

The choice lives in player data (Fabric Data Attachment) and survives death. Powers are granted
from the source `yggdrasil_origins:class`, so `/reload` and class changes re-grant them cleanly
without piling anything up.

## Balance

### Impact tiers

Every origin carries an impact tier, and it matches the **actual sum of its numbers** rather
than an impression:

| tier | origins | swing | net |
|---|---|---|---|
| 0 — none | human | 0 | 0 |
| 1 — low | halfling, molfar, serpentfolk, mavka | 2.3 | −0.3 |
| 2 — medium | elf, angel, berehynia, kharakternyk, nichnytsia, tiefling | 3.3 | −0.5 |
| 3 — high | dwarf, blazing, half-giant, undead, vodianyk, rusalka, horyn, povitrulia, zaliznyak, orc, werewolf, dragonborn | 3.8–4.7 | −0.8 |

"Swing" is the sum of every attribute change by absolute value; "net" is pluses minus minuses.
**No origin has a positive net**: risks outweigh the gain everywhere, and the tier only says how
strongly a class changes the game, not how much stronger it is. The higher the tier, the larger
the swing — and the more a mistake costs.

Paths are a separate, much smaller layer: there gain and cost are balanced to roughly zero, so a
path is a trade rather than free growth.

Rule of thumb when editing: **the downside has to hit the currency the class plays with.**
Nerfing heavy weapons for a mage, or a negative `knockback_resistance`, is decoration, not a cost.

### Human

The first entry in the class layer is **Human**: zero abilities, zero attribute changes, zero
visual parts. Exactly a vanilla player, the way "No Path" works in the path layer. It has no
paths of its own, so after choosing it the path screen **does not open**: a layer left with a
single option that is also the default fills itself in, instead of making the player press a
button on a one-row screen. The same now applies to the other classes without paths (angel,
vodianyk, mavka, rusalka, halfling, dragonborn).

### Item, potion and block mechanics

These rest **only on vanilla items and the mod's own tags** (`data/yggdrasil_origins/tags/`), so
everything is edited in one place.

| origin | mechanic | cost |
|---|---|---|
| undead | carrion (rotten flesh, spider eyes, poisonous potatoes) does not poison and feeds +50% | any normal food feeds −35% |
| blazing | 30% chance to get a **finished ingot** instead of iron/gold/copper ore | beneficial potions last −35% |
| undine | beneficial potions last +40% | harmful effects last +40% too |
| orc | raw meat and fish do not poison, feed +40% and grant strength for 8 s | cooked food feeds −25% |
| geonite | stone, deepslate, tuff, basalt and netherrack break **by hand** | mining speed −12% |
| halfling | beneficial potions last **twice as long** | and are one level weaker |

## The power engine

The mod is **self-contained**: `depends` holds only `fabricloader`, `minecraft` and `fabric-api`.
Neither Origins nor Apoli is needed to play or to build.

### What the engine supports

| group | types |
|---|---|
| attributes | `attribute`, `conditioned_attribute`, `multiple` |
| passives | `night_vision`, `invisibility`, `effect_immunity`, `fire_immunity`, `walk_on_fluid`, `ignore_water`, `entity_glow`, `disable_regen` |
| periodic and state | `action_over_time`, `burn`, `cooldown`, `resource` |
| combat | `action_when_hit`, `attacker_action_when_hit`, `target_action_on_hit`, `prevent_death`, `modify_damage_taken`, `modify_damage_dealt`, `modify_projectile_damage` |
| items and world | `restrict_armor`, `prevent_item_use`, `modify_food`, `modify_status_effect_duration`, `modify_status_effect_amplifier`, `modify_exhaustion`, `modify_harvest`, `action_on_block_break` |
| actions | `sequence`, `random_chance`, `heal`, `damage`, `apply_effect`, `clear_effect`, `play_sound`, `gain_air`, `give`, `random_teleport`, `spawn_entity`, `trigger_cooldown`, `change_resource`, `set_resource` |
| conditions | 29 entity conditions (light, sun, fire, snow, rain, thunder, submersion, dimension, health, fall distance, movement, sneaking, sprinting, swimming, effects, item in slot, block underfoot, entities and blocks in radius, time of day, cooldown, resource), item ones (`ingredient`, `empty`, `armor_value`), block ones (`in_tag`), damage sources (`type`, `projectile`, `fire`, `in_tag`, `explosive`, `from_falling`, `bypasses_armor`) and hit targets — all with `inverted` |

Where Fabric events do not reach (damage amount, food, effects, exhaustion, harvesting, natural
regeneration, fluid physics) there are **our own mixins into Minecraft** — never into other mods.

### Decisions baked into the engine

* **RPG attributes are a soft dependency.** If an attribute is not in the registry the modifier
  is skipped with a warning and the mod still runs on plain Fabric.
* **Transient modifiers plus auto-cleanup.** The engine never writes its modifiers into player
  data and, before each application, strips everything in the `yggdrasil_origins` namespace from
  all attributes (including leftovers from versions that ran through Apoli).
* **A client mirror.** Lava physics and the wounded-enemy glow are drawn on the client, so the
  server sends three flags (`walk_on_lava`, `walk_on_water`, `glow_wounded`) with the class snapshot.
* **Foreign data cannot break startup.** A power from another datapack that fails to parse is
  simply not picked up.

### Extra tools the shipped classes do not use

Three mechanics live in the engine that **no class or path JSON in this mod enables**. They are
building blocks: if they are ever wanted, a power in the data is enough, no code change needed.

* **noticeability** — a multiplier on how far away mobs notice the player:

  ```json
  { "type": "yggdrasil_origins:nature", "notice": 0.6 }
  ```

  Below 1 means noticed later, above 1 sooner. It scales
  `LivingEntity#getVisibilityPercent`, so sneaking and mob headwear keep working as always.

* **vulnerability to the attacker's weapon** — two damage conditions:

  ```json
  { "type": "apoli:modify_damage_taken",
    "modifier": { "operation": "multiply_base_additive", "amount": 0.3 },
    "damage_condition": { "type": "yggdrasil_origins:attacker_enchantment",
                          "enchantment": "minecraft:smite", "min_level": 1 } }
  ```

  and `yggdrasil_origins:attacker_item` with an `item_condition`, for when the item itself
  (material, tag) in the attacker's main hand matters.

* **entity families** — the condition `yggdrasil_origins:entity_tag` with vanilla tags
  (`minecraft:undead`, `arthropod`, `aquatic`, `illager`). It fits both `target_condition` in
  `modify_damage_dealt` and anywhere a living entity is accepted.

The enchantment level is read through the world registry: in 1.21 enchantments are a dynamic
registry and the holder in an item component does not always carry an unwrapped key, so a naive
comparison would silently fail.

## RPG stack attributes

Most abilities are attribute modifiers that **do not exist in vanilla**. The pack mods provide
them, and all of them are declared as `suggests` in `fabric.mod.json`: a missing mod costs you
its modifiers, not the whole class.

| mod id | attribute namespace | what it gives |
|---|---|---|
| `spell_power` | `spell_power:` | magic schools: `fire`, `frost`, `water`, `earth`, `air`, `arcane`, `healing`, `soul`, `nature`, `lightning`, plus `haste`, `critical_chance`, `critical_damage`, `generic` |
| `spell_engine` | `spell_engine:` | `damage_taken`, `healing_taken`, `evasion_chance` |
| `mrpg_lib` | `mrpg_lib:` | procs and fuses: `*_fuse_modifier`, `lifesteal_modifier`, `spell_vampire`, `tenacity`, `burning_chance`, `freeze_chance`, `poison_chance`, `bleeding_chance`, `stagger_chance`, `armor_piercing`, `damage_reflect_modifier` |
| `attributes_ld` | `attributes_ld:` | damage by weapon type: `claymore`, `hammer`, `mace`, `axe`, `dagger`, `glaive`, `spear`, `sickle`, `knuckles`, `stave`, `wand`, plus `warrior/rogue/paladin_weapon_damage`, `archer_melee_damage`, `shield_bonus` |
| `combat_roll` | `combat_roll:` | `distance`, `count`, `recharge` |
| `ranged_weapon_api` | `ranged_weapon:` | `damage`, `haste`, `pull_time`, `velocity` |
| `critical_strike` | `critical_strike:` | `chance`, `damage` |

Our own attribute (nothing to install, it is inside the mod):

| namespace | attribute | mechanic |
|---|---|---|
| `yggdrasil_origins` | `swim_speed` | horizontal speed multiplier in water (`SwimSpeedMixin`) |

> **The `more_rpg_classes` namespace is dead.** `more_rpg_library` was renamed to `mrpg_lib`
> and its attribute namespace changed with it. `checkOrigins` fails the build on the old ids.

### Operation rule (otherwise a modifier does nothing)

`add_multiplied_base` means `amount x base_value`, so the right operation depends on the base
the attribute has in the pack:

| attributes | base | operation for "+/-X%" |
|---|---|---|
| `spell_power:<school>` (fire, frost, water, earth, air, arcane, healing, soul, nature, lightning) | 1.0 | **`add_multiplied_total`** |
| `ranged_weapon:damage`, `velocity`, `pull_time` | 0 / 1.0 (the weapon supplies it) | **`add_multiplied_total`** |
| `spell_power:generic`, `haste`, `critical_chance` | 100 | `add_multiplied_base` |
| `spell_engine:damage_taken`, `healing_taken`, `evasion_chance` | 100 | `add_multiplied_base` |
| `mrpg_lib:*` | 100 | `add_multiplied_base` |
| `critical_strike:chance`, `damage` | 100 | `add_multiplied_base` |
| `attributes_ld:*` | 0, but the mod sums modifiers by operation itself | `add_multiplied_base` |
| `combat_roll:distance` (3), `recharge` (20), `count` (1) | non-zero | `add_multiplied_base` / `add_value` |
| vanilla (`max_health`, `armor`, `knockback_resistance`, ...) | non-zero | `add_value` or `add_multiplied_base` |

Separately: a negative on an attribute whose `min == base` **does nothing**. That covers
`knockback_resistance` (min 0), `oxygen_bonus` (min 0), every `mrpg_lib:*` and
`critical_strike:*` (min 100). Class downsides must go through `spell_engine:damage_taken +%`,
`max_health`, `armor`, speed or conditional penalties instead.

### RPG Series item tags

For item conditions (`apoli:ingredient`, `restrict_armor`, `prevent_item_use`) the pack provides
ready tags in the `rpg_series` namespace:

* `rpg_series:weapon_type/<type>` — `claymore`, `dagger`, `glaive`, `hammer`, `mace`, `spear`,
  `sickle`, `sword`, `double_axe`, `short_bow`, `long_bow`, `heavy_crossbow`, `rapid_crossbow`,
  `damage_staff`, `healing_staff`, `damage_wand`, `healing_wand`, `spell_blade`, `spell_scythe`, `shield`
* `rpg_series:armor_type/<type>` — `melee`, `magic`, `archery`
* `rpg_series:archetype/<role>` — `melee_damage_weapon`, `ranged_damage_weapon`,
  `magic_damage_weapon`, `healing_weapon`, `defense_weapon`

### Apoli version compatibility

`apoli:apply_effect` in **Apoli 2.12.0-pre.2** (the version in FallenEden) reads the effect as
`{"effect": "...", "duration": N}`, while **pre.3** reads `{"id": "...", "duration": N}`. The
data therefore carries **both keys at once**, so the files load on either version, and
`checkOrigins` fails if someone leaves only one. The validator also enforces: `apoli:give` takes
its stack through `"id"`, sound ids are dotted (`minecraft:item.totem.use`), and every reference
to a `yggdrasil_origins:*` tag must exist under `data/yggdrasil_origins/tags/`.

## Two selection layers: race and path

`selection/class.json` is the race, `selection/path.json` is a specialisation of that race. A
path entry carries `"requires": "<class>"`, so the picker only offers the paths of the race that
was chosen. `"default": "yggdrasil_origins:path_free"` is the neutral "No Path".

The layers are applied in `order`. A choice in an earlier layer can invalidate a later one — in
that case the later choice is cleared and the player is asked again.

## The picker screen

One screen, everything visible at once: a searchable list on the left, details in the middle, a
live portrait on the right.

* search by name and description, plus a filter by impact tier;
* the selection frame **glides** between rows instead of jumping;
* after a search or a filter the rows fade in from the top;
* the portrait shows the player with the looks of the highlighted class and turns slowly; it
  briefly "breathes" when the selection changes, so the swap is noticed;
* the background and panels are a single flat tone — a full-height gradient with a small colour
  difference breaks into visible bands at GUI scale 2 on a 2K screen;
* `Backspace` goes back a layer, `Enter` confirms, a double click chooses.

The same screen in read-only mode is the **"My Class"** reference: key **L** or `/yggclass`. It
lists what you have chosen in every layer with the full ability text and the portrait, and has
no picker buttons. It asks the server for nothing — the client snapshot already holds everything.

## Class looks

Each class may carry a `visual` block: body proportions, a tint and a list of parts.

```json
"visual": { "height": 0.95, "width": 1.08, "tint": "#86C06A",
            "parts": ["fangs", "frill"] }
```

* **both the model and the hitbox** come from one source (`visual/VisualSource.java`), so
  collisions never drift from what you see;
* **width fits two blocks** and **height fits two blocks** for every class: the height
  multiplier is capped at 1.11, so the tallest class is 1.8 x 1.11 = 1.998 blocks and still
  walks under a two-block ceiling without suffocating;
* **armour and held items scale with the body** — vanilla and RPG Series alike, because they go
  through the same transformation;
* **parts hide under armour** where it makes sense: beast ears, horns, antennae and brows under
  a helmet, carapace and pauldrons under a chestplate. Elf ears deliberately stay visible;
* ears, brows and hair tufts take their colour from the **player's own skin** (drawn against the
  head UV); everything else uses `textures/entity/visual_parts.png`.

### Texture conventions

The texture is generated by `tools/gen_visual_texture.py`, which also validates the geometry.

* every part owns a region, and inside it **each box face** (top, bottom, sides, front, back) is
  painted with its own lighting, so a part reads as a solid object rather than a flat blob;
* on top of that each face gets a **bevel**: a lighter edge at the top left, a darker one at the
  bottom right;
* key parts are built at **double density** — the model box is twice as large and shrinks by half
  when drawn, so four times as many texels land on it: horn rings, beard strands, feather shafts
  and individual scales become visible;
* **a region is always filled completely.** Several boxes of different size can share a region,
  and a smaller one unwraps differently; without a full fill some of its faces would land on
  transparent pixels, turn invisible, and you would see the inside of the part.

### Part colour

The class tint is **multiplied** by the part colour, so a dark base darkens twice. That used to
leave tiefling horns nearly black (brightness 22 of 255) and the dwarf beard at 38, while orc
tusks sat at 234 — the family looked assembled from different mods. Fixed on both sides: the
base colours in the generator are lifted to a common target brightness (each keeping its own
hue), and the class tint is taken at **half strength for solid parts**. Glowing parts (sparks,
halo, crescent, wisps) still take it in full, because their base is white. The spread is now
91…234 instead of 22…234.

Three checkers live in `tools/` and should be run after any geometry change:

```
python3 tools/gen_visual_texture.py   repaints the texture and verifies every box fits its region
python3 tools/check_uv.py             scans for transparent pixels under real box UVs
python3 tools/check_symmetry.py       compares *_left / *_right pairs: pivots, angles, boxes, .mirror()
```

### Animations

Almost nothing stands still: tails ripple segment by segment, wings fold behind the back and
spread in the air, fins quiver in water, gills move only while submerged, a serpentfolk frill
flares when running, the halo turns and breathes, antennae sway out of step with each other, the
beard lags behind the walk, and a beast ear flicks every few seconds — first one, then the other.

Two sign conventions are easy to get wrong, and both were real bugs:

* in model space **+Y points down**, so a *positive* `xRot` lifts a part that extends along `+Z`.
  A tail needs a negative `xRot` to hang back and down;
* for the right wing a *positive* `yRot` sweeps it **back behind the spine** (a negative one
  throws it forward along the arms) and a positive `zRot` lifts the tip. The left wing mirrors
  both signs. The folded sweep is kept near 0.5 rad: more than that and the wings cross over the back.

While sneaking the torso pitches forward by about half a radian and parts attached to it go
along, so wings and tails get a counter-correction — otherwise they ride up over the head.

### Cost and the player's switch

Visual parts are drawn only within 64 blocks, and small details only within 20. A class adds at
most about ten extra boxes to a player. Any player can turn the looks off entirely for
themselves with `/yggvisuals` or a key in the controls; the server is not involved, and hitboxes
keep following the server so movement cannot rubber-band.

## Ability bars (HUD)

Cooldowns and resources are drawn to the left of the hotbar and are animated: they fade in and
out, a resource creeps towards its new value instead of jumping, and a cooldown flashes briefly
just before it is ready so it is caught by the corner of the eye. A resource with a small range
is split into ticks (3/5 is readable without the numbers); with a large range it stays a solid
bar, because a hundred marks on 76 pixels would be a smear.

A player can hide the bars with `/ygghud`.

## The class orb

`yggdrasil_origins:class_orb` clears the choice and opens the picker again. Craftable from 4 gold
ingots and an eye of ender (see the server checklist if you would rather it were not).

## Localisation

**Every string a player can see is a translation key.** Nothing user-facing is hardcoded: class
and ability names, descriptions, screen labels, command feedback, item names and HUD units all
live in `assets/yggdrasil_origins/lang/*.json`. The mod ships `en_us` and `uk_ua`; the code
itself, including comments and log lines, is English only.

Anyone can change the wording or add a language **without touching the jar**:

* **a resource pack** — put `assets/yggdrasil_origins/lang/<locale>.json` in it with only the
  keys you want to change; Minecraft merges it over ours. This is the normal way to translate
  the mod into a new language or to reword the classes for your lore;
* **a server resource pack** — the same file served through `resource-pack` in
  `server.properties`, if you want every player on the server to see your wording. Command
  feedback is sent as translatable components and resolved on the client, so a client-side pack
  governs it;
* **datapacks can add content but not translations**: `data/` holds classes, powers and tags,
  while text lives under `assets/`. A datapack that adds its own classes should ship the
  matching resource pack with its own lang file — or simply use its own namespace keys.

Key shapes, if you are overriding them:

```
origin.yggdrasil_origins.<class>.name / .description
power.yggdrasil_origins.<power>.name / .description
layer.yggdrasil_origins.<layer>.name
gui.yggdrasil_origins.picker.*          picker screen labels
command.yggdrasil_origins.*             command feedback
message.yggdrasil_origins.*             action-bar messages
key.yggdrasil_origins.*                 keybind names
item.yggdrasil_origins.class_orb        item name and tooltip
hud.yggdrasil_origins.seconds           the seconds suffix on cooldown bars
```

`checkOrigins` fails the build when a class or ability is missing a key in **any** shipped
language, so a half-translated release cannot happen by accident.

## Adding a new class

```
./gradlew newOrigin -Pid=paladin -Picon=minecraft:shield -Pimpact=2
./gradlew newPower  -Pid=paladin_oath -Porigin=paladin
./gradlew checkOrigins
```

`newOrigin` creates the class file, appends it to the selection layer and adds TODO keys to
**every** lang file at once, so no language falls behind. `removeOrigin -Pid=<id>` deletes the
class together with the powers only it used and the matching translation keys.

Then describe the abilities in `powers/`, replace the TODO text, and run `checkOrigins`.

## Validation

```
./gradlew checkOrigins     runs automatically as part of build
```

What it checks:

1. JSON syntax of every resource file;
2. layers against origins: a layer that references a missing origin, a `"requires"` pointing at
   a missing class, an origin that is in no layer at all;
3. origins against powers: a missing power, a power no origin uses (powers granted by other
   powers count as used);
4. attribute ids against `known_attributes.txt`, which is generated from the real pack jars:

   ```
   ./gradlew scanAttributes -PmodsDir=/path/to/pack/mods
   ```

   Any attribute that no mod in the pack provides fails the build — this is what catches a
   renamed namespace such as the dead `more_rpg_classes`;
5. version-sensitive formats: the dual `apply_effect` keys, `apoli:give` using `"id"`, dotted
   sound ids, and references to tags that must exist under `data/yggdrasil_origins/tags/`;
6. translations in **every** lang file, plus orphan keys that belong to nothing.

## Power JSON reference

### Skeleton

```json
{
  "type": "apoli:attribute",
  "modifier": { "id": "yggdrasil_origins:<power>_<attr>",
                "attribute": "minecraft:generic.max_health",
                "amount": 4, "operation": "add_value" },
  "condition": { "type": "apoli:sneaking" }
}
```

Every modifier needs a unique `id` in our namespace — that is what lets the engine strip exactly
its own modifiers and nothing else.

### Frequently used types

| type | purpose |
|---|---|
| `apoli:attribute` / `apoli:conditioned_attribute` | permanent or conditional attribute change |
| `apoli:multiple` | several sub-powers in one file |
| `apoli:action_over_time` | an action every N ticks |
| `apoli:action_when_hit`, `apoli:target_action_on_hit` | combat reactions |
| `apoli:modify_damage_taken` / `_dealt` / `_projectile_damage` | scaling damage |
| `apoli:prevent_death` | a death save, usually paired with a cooldown |
| `apoli:cooldown`, `apoli:resource` | state with an optional HUD bar |
| `apoli:modify_food`, `apoli:modify_status_effect_duration` | food and effects |
| `apoli:restrict_armor`, `apoli:prevent_item_use` | gear restrictions |

### Entity actions (`entity_action`)

`heal`, `damage`, `apply_effect`, `clear_effect`, `play_sound`, `gain_air`, `give`,
`random_teleport`, `spawn_entity`, `trigger_cooldown`, `change_resource`, `set_resource`,
composed with `sequence`, `random_chance` and `target_action`.

### Entity conditions (`condition`)

Light and sky (`brightness`, `exposed_to_sky`, `exposed_to_sun`, `in_rain`, `in_snow`,
`in_thunderstorm`, `time_of_day`), state (`health`, `relative_health`, `on_fire`, `invisible`,
`sneaking`, `sprinting`, `swimming`, `moving`, `fall_distance`, `submerged_in`, `status_effect`),
world (`dimension`, `on_block`, `block_in_radius`, `entity_in_radius`), gear
(`equipped_item`, `head`, `chest`, `legs`, `feet`, `mainhand`, `offhand`), our own state
(`power_active`, `resource`), and the combinators `all_of`, `any_of`, `constant` — all accept
`"inverted": true`.

### Value modifiers (`modifier` in modify_* powers)

`multiply_base_additive` (the usual "+/-X%"), `add_base_early`, `add_base_late`,
`multiply_base_multiplicative`.

## Performance

Measured with `/ygg perf` on a live server tick, with a heavy class:

```
engine tick: average 5.0 us, peak 33.1 us over 604 ticks (50000 us = a whole server tick)
```

The engine keeps a prepared per-player layout, so a tick only walks what actually has to move;
packets are sent only on change, profiles only to players who can see each other, and the render
layer skips detail at distance. A dedicated server starts in about half a second and writes one
line to the log — everything else is logged only when something is wrong.

## Development

```
./gradlew build                              builds the jar and runs checkOrigins
./gradlew runServer                          dedicated server
./gradlew runClient -PquickPlay="New World"  the client jumps straight into a world
./gradlew runClient -PquickName=Tester       a fixed player name, handy for command tests
```

The RPG stack mods are not pulled by Gradle; for a dev run drop them into `run/mods/` from the
pack (`~/.local/share/ua.com.minestar.launcher/packs/falleneden/mods/`). Without them the mod
still starts — the affected modifiers are skipped and `/ygg doctor` lists them.

If a dependency change ever produces `AbstractMethodError` or `NoSuchMethodError`, clear the
Loom remap cache and run again:

```
rm -rf .gradle/loom-cache/remapped_mods
```

## Testing

Beyond `checkOrigins`, the mod is verified by running it:

* a dedicated server start, confirming the registry line and a clean log;
* datapack functions driving `/ygg` commands with `execute store result score` assertions —
  that is how multi-target selectors, class switching and the ability counts are checked;
* in-game screenshots from four angles for every visual part, which is how the wing sign error,
  the broken crescent and the dark-tint problem were found;
* `/ygg perf` for the tick cost and `/ygg doctor` for the attribute health.
